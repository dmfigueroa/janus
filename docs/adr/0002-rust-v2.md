# ADR 0002: Rust v2

- Status: Accepted

## Context

Janus shares a resource-constrained deployment host with multiple applications. The owner requires Rust and wants a frontend without compilation while preserving the existing application. There is no numeric resource budget; resource savings must be measured rather than assumed.

## Decision

Replace the web stack with Rust while preserving v1 features, stored data, domain rules, supported integrations, appearance, navigation, and interaction quality. Allow small visual differences from replacing Chakra; substantial redesign is a separate decision. Preserve externally observable MCP contracts, including transport behavior. Compatibility with v1 web URLs and its internal request protocol is not required.

Use Axum and Tokio for HTTP, Askama for HTML templates, SeaORM for database mapping, and the official `rmcp` SDK for MCP. SeaORM remains conditional on proving compatibility with existing stored values and behavior. The frontend uses htmx, SortableJS, plain CSS, and small JavaScript modules. Pin and serve browser-ready assets locally. Coolify compiles Rust and Askama on the existing build server and deploys images to the separate deployment server; browser JavaScript and CSS require no compilation or bundling. V2 has no Node runtime or production CDN dependency.

Start with one feature-organized Rust crate under `v2/` alongside v1. One Rust process serves pages, fragments, static assets, and MCP. Thin web and MCP handlers call shared feature operations, with ORM entities and provider adapters behind those operations. V2 implements its own business behavior rather than calling the running v1 application. Split crates only for a concrete need. Apply the repository's feature ownership principles without reproducing TanStack-specific boundaries.

Both versions run on the same host and access the same local SQLite database. Preserve its schema and stored-value semantics until v1 is completely deprecated. V1 alone owns schema migrations during coexistence; v2 checks compatibility at startup and never creates, migrates, or auto-synchronizes schema objects, including ORM migration metadata. Reject a missing or incompatible database rather than create an empty replacement. A separate production database and final data transfer are not the transition model.

Deploy separate v1 and v2 Compose services within the same Coolify application, mounting the existing database directory. Preserve its actual volume identity and file location. V2 is deployed during development with separately routable, protected testing surfaces; existing MCP clients continue using v1. Retain the existing Cloudflare Access boundary rather than introduce another identity system.

Open v2 pages need not update automatically after v1 or MCP writes. Changes can appear on navigation, refresh, or a relevant action. Actions validate current database state and reconcile their displayed results.

## Consequences

Avoiding frontend compilation does not eliminate client-side interaction code. Browser-ready libraries support the chosen approach, but keyboard behavior, focus, touch scrolling, failure recovery, and fragment lifecycle coordination remain application responsibilities. Preserve anchor-based ordering against the complete stored watchlist rather than overwrite hidden items from a filtered subset. The [htmx sortable example](https://htmx.org/examples/sortable/) demonstrates library integration, not Janus parity or measured resource savings.

Sharing SQLite avoids a production data transfer but requires cross-version compatibility, bounded connection and lock handling, and preserved transaction semantics. ORM mappings must account for timestamps, application-side update hooks, nullable booleans, JSON text, Unicode matching, and existing defaults. Keep transactions short and do not hold write transactions across provider HTTP calls or blindly retry ambiguous commits. Automated compatibility tests use disposable databases created through v1 migrations; deployed v2 uses the shared production database.

Record the v1 parity baseline when implementation begins and explicitly track later v1 changes. Prove database compatibility and the complete watchlist-reordering interaction through web and MCP before broader porting. V1 remains operational until the complete parity checklist passes and the owner accepts the actual application. Automated checks alone do not authorize retirement. Cutover and rollback planning remain deferred until v2 is done.

This decision supersedes [ADR 0001](0001-chakra-ui-foundation.md)'s Chakra requirement for v2. ADR 0001 continues to govern v1.

## Implementation Notes

- **Deployment:** V1 and v2 can run either as separate container applications or together via `deploy/compose.yaml`, provided both mount the same SQLite directory and route `/v2` to v2 (see [`deploy/README.md`](../../deploy/README.md)).
- **Browser assets:** In addition to htmx and SortableJS, v2 also vendors browser-ready Open Props CSS tokens locally under `v2/static/vendor/` (see [`v2/static/vendor/README.md`](../../v2/static/vendor/README.md)).
