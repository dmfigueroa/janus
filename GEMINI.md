# Janus Project Rules & Guidelines

## 1. Project Overview

Janus is a premium watchlist application designed to track movies and TV shows
in release order. The project prioritizes a high-quality, responsive user
experience with a modern aesthetic.

## 2. Technology Stack

- **Framework**: TanStack Start
- **Database**: SQLite (via Drizzle ORM with migrations)
- **Deployment**: Docker
- **UI Styling**: Tailwind CSS v4
- **Component Library**: shadcn/ui
- **Runtime/Package Manager**: Node.js (via npm)

## 3. Core Principles

- **Minimal Dependencies**: Avoid adding new dependencies unless absolutely
  necessary. Prefer implementing simple utilities over importing heavy
  libraries.
- **Functional Programming**: Use functional patterns where possible. Avoid
  class-based components or complex object-oriented patterns unless required by
  the framework.
- **Simplicity**: Write code that is easy to read and maintain. Complexity
  should be isolated.
- **Type Safety**: strict TypeScript usage. No `any` type allowed.

## 4. Design & Aesthetics

- **Visual Style**: Premium, modern, and vibrant.
- **Theme**: Dark mode by default with vibrant accent colors (e.g., deep reds,
  glassmorphism effects).
- **Interactivity**: Use subtle micro-animations and transitions to make the app
  feel "alive".
- **Typography**: Clean, sans-serif fonts (e.g., Inter, Outfit).
- **Components**: Use shadcn/ui components as a base, but customize them heavily
  to match the premium brand.

## 5. Development Workflow

- **Package Management**: Always use `npm` for installing packages and running
  scripts.
- **Database**:
  - Use Drizzle Kit for migrations.
  - Ensure `schema.ts` is the source of truth.
  - Run migrations manually or via a controlled script, verifying against the
    local SQLite file.
- **Styling**:
  - Use Tailwind v4 for all styling.
  - Avoid standard CSS files where utility classes can suffice, except for
    global themes/animations.
  - Design first: Ensure the UI "wows" before considering the task complete.

## 6. Directory Structure

- `src/routes`: TanStack Start file-based routing.
- `src/components`: Reusable UI components.
- `src/db`: Drizzle schema and connection logic.
- `src/utils`: Helper functions (keep minimal).

## 7. Best Practices

- **Server State**: Leverage TanStack Query (via TanStack Start) for data
  fetching.
  - **IMPORTANT**: When defining server functions with `createServerFn`, ALWAYS
    use `.inputValidator((data) => schema.parse(data))` instead of
    `.validator(schema)`. The `.validator` method does not exist on the current
    version of TanStack Start used in this project.
- **Validation**: Use Zod for schema validation (forms, API responses).
- **Accessibility**: Ensure all components are accessible (aria labels, keyboard
  nav).
- **Docker**: Ensure the app builds and runs correctly in a containerized
  environment.

## 8. Critical Implementation Notes (LLM Guidelines)

- **Data Fetching Strategy**:
  - **Prefer Route Loaders**: Always fetch initial route data server-side using
    the `loader` function in `createFileRoute`.
  - **Consume with `useLoaderData`**: Access this data via
    `Route.useLoaderData()`.
  - **Avoid `useQuery` for Route Data**: Do not use client-side `useQuery` for
    primary route data; it causes waterfalls and hydration mismatches in this
    specific stack.

- **Loading States**:
  - **Subtle Loading**: Use `useRouterState` (checking `isLoading`) to show
    spinners or progress bars while keeping the current page visible.
  - **Avoid `pendingComponent`**: Unless you want to completely unmount the
    current view and show a full-page skeleton, avoid `pendingComponent` as it
    can feel jarring.

- **Imports**:
  - **Relative over Alias**: If you encounter "Failed to resolve import" errors
    with `@/...`, fallback to relative imports (e.g.,
    `../../components/ui/...`).

- **Server Functions**:
  - **Validator**: MUST use `.inputValidator((d) => schema.parse(d))` for
    `createServerFn`. usage of `.validator(schema)` will fail.

- **Testing**:
  - **Typed Mocks**: When using Vitest, prefer `vi.mocked()` for typed mocks instead of casting to `any`.
  - **Avoid `any`**: Maintain strict type safety in tests; avoid using the `any` type.

- **Package Management Integrity**:
  - **Do NOT manually edit `package-lock.json`**: This file is generated by `npm install` and should be respected.
  - **`"peer": true` is valid**: Do not remove `"peer": true` entries from `package-lock.json`; they are standard in modern npm/Node versions.
  - **Use `npm install`**: To fix lockfile issues, run `npm install` rather than editing the file directly.
